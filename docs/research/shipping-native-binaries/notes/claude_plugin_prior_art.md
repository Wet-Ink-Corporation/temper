# Prior art: how Claude Code plugins and MCP servers ship native Rust and Go binaries (as of October 2026)

Research date: 2026-10-01. The GitHub repos and docs pages below were fetched on that date. Wherever I could, I read the launcher code itself and not only the README. Each finding says which of the two it comes from.

## Q1: Which public plugins ship native binaries, where the binary comes from, and what launches it

### Takeaway
The pattern that recurs most in real plugins is a small launcher committed to the plugin. It can be a POSIX `sh` script, a `.cmd` file, or a Node script. The launcher reads the version from the plugin's own `plugin.json`, then downloads the matching GitHub-release asset into `${CLAUDE_PLUGIN_DATA}`, verifies its SHA-256 against the release `checksums.txt` (only the better ones do this), writes it atomically and `exec`s it. The MCP `command` or the hook points at that launcher. A second large group commits no binary at all and assumes the user already installed the CLI (Homebrew, Scoop, `cargo install`, npm). Anthropic's own LSP plugins do this, and so do beads and cadence-hooks.

### Cited Findings

**A. Launcher downloads the release binary on first run into CLAUDE_PLUGIN_DATA (code verified)**

- **dimitar-grigorov/mcp-file-tools** (Go MCP server). `.mcp.json` sets `"command": "node", "args": ["${CLAUDE_PLUGIN_ROOT}/bin/run.js"]`. `run.js` takes the version from `require('../.claude-plugin/plugin.json').version`. It maps `process.platform`/`process.arch` to `{windows,darwin,linux}×{amd64,arm64}` and caches the binary at `${CLAUDE_PLUGIN_DATA}/bin/mcp-file-tools-v<ver>-<os>-<arch>[.exe]`, falling back to `~/.cache/mcp-file-tools`. It downloads the asset and `checksums.txt` in parallel, refuses to run on a SHA-256 mismatch, writes `<bin>.<pid>.tmp` with mode 0755, renames it into place, then spawns the binary with `stdio: 'inherit'`. Logs go to stderr only. A code comment explains the choice of Node: it "runs the same on Windows/macOS/Linux and avoids the 'bash resolves to WSL' problem when Claude Code spawns the server without a shell". The repo also has a POSIX `plugin/launcher/mcp-file-tools` script that does the same steps with curl/wget and sha256sum/shasum, plus a Go `cmd/mcp-file-tools-launcher` (`install_windows.go`) for Windows. That Go launcher reads `plugin.json`, rejects version strings containing non-version characters before they go into a URL, and verifies checksums. — [run.js](https://github.com/dimitar-grigorov/mcp-file-tools/blob/main/plugin/bin/run.js), [sh launcher](https://github.com/dimitar-grigorov/mcp-file-tools/blob/main/plugin/launcher/mcp-file-tools), [install_windows.go](https://github.com/dimitar-grigorov/mcp-file-tools/blob/main/cmd/mcp-file-tools-launcher/install_windows.go), [.mcp.json](https://github.com/dimitar-grigorov/mcp-file-tools/blob/main/plugin/.mcp.json)
- **liliang-cn/cortexdb** (Go MCP server, one launcher shared by its Claude Code and Codex plugins). `.mcp.json` sets `"command": "${CLAUDE_PLUGIN_ROOT}/bin/cortexdb-mcp"`, a `#!/bin/sh` script that sits next to a `cortexdb-mcp.cmd` for Windows. Both launchers key the cache on the plugin version read from `plugin.json`. If the version can't be read they fall back to `releases/latest/download`. They download with curl/wget (`.cmd`: PowerShell `Invoke-WebRequest`), `chmod +x`, `mv` into place, and delete older cached versions. A `CORTEXDB_MCP_BIN` env var overrides the download. **There is no checksum verification.** The `.cmd` file parses `plugin.json` through `powershell ConvertFrom-Json` and assumes amd64 unless `PROCESSOR_ARCHITECTURE` is ARM64. The plugin keeps these launchers in a top-level `bin/` directory, which claude.ai org sync rejects (see Q3). — [cortexdb-mcp](https://github.com/liliang-cn/cortexdb/blob/main/plugins/cortexdb/bin/cortexdb-mcp), [cortexdb-mcp.cmd](https://github.com/liliang-cn/cortexdb/blob/main/plugins/cortexdb/bin/cortexdb-mcp.cmd)
- **tweag/tricorder** (`tricorder-mcp`, launched by a bash wrapper at `agent-plugins/tricorder-mcp/servers/tricorder-mcp`). It caches in `${CLAUDE_PLUGIN_DATA}/servers` and also accepts a generic `${PLUGIN_DATA}` "for agent harnesses that use the generic agent-plugins.org variable name". Instead of pinning to the plugin version it **self-updates**: once every 24 h it asks the GitHub API for the newest `tricorder-mcp-*` tag and re-downloads the binary if the tag changed. When the network fails it uses the cached binary. It publishes only `x86_64-linux` and `aarch64-darwin`. On any other platform it prints a "build from source and point the MCP command at it" message and exits 1. No checksum. — [wrapper](https://github.com/tweag/tricorder/blob/main/agent-plugins/tricorder-mcp/servers/tricorder-mcp)
- **brunoborges/ghx** (Go `ghx`/`ghxd`). `agent-plugin/scripts/install.sh` installs into `${CLAUDE_PLUGIN_DATA}/bin`, falling back to `~/.ghx-plugin/bin`, and exits early if the binaries are already present. It resolves the "latest non-`plugin-*` tag" through the GitHub API, which means the binary version is **not** pinned to the plugin version. It downloads a tarball, does no checksum check, and supports linux/darwin × amd64/arm64. If no real `gh` is on PATH it installs a `gh` shim. The repo also ships an `install.cmd`. — [install.sh](https://github.com/brunoborges/ghx/blob/main/agent-plugin/scripts/install.sh)
- **berk-karaal/claude-code-notification** (Go). RELEASING.md, which documents the intended design (I did not read the scripts themselves), says the version lives in `plugin/.claude-plugin/plugin.json`. CI fails if the `v*` tag doesn't match that version. GoReleaser builds darwin/linux × amd64/arm64 tar.gz files plus `checksums.txt`. A **`SessionStart` hook** (`on-session-start.sh`) downloads `notification_{os}_{arch}.tar.gz` into `${CLAUDE_PLUGIN_DATA}/bin/notification` unless `--version` already matches. "All errors are logged to `${CLAUDE_PLUGIN_DATA}/logs/notification.log` but never block the Claude session (the script always exits 0)". Before dispatching, the per-event hook `on-hook.sh` re-checks that the binary version matches. No Windows target is listed. — [RELEASING.md](https://github.com/berk-karaal/claude-code-notification/blob/main/RELEASING.md)
- A GitHub code search for `CLAUDE_PLUGIN_DATA` together with `releases/download` turned up the same pattern in more repos that I did not read closely: high5-ventures/apple-reminders-for-claude (`scripts/install-binary.sh`), replygirl/nearest-neighbor (`install-nbr.ps1`), reboot-dev/reboot (`install_envoy.sh`, `install_cloudflared.sh`), trustabl/agent-reliability-analyzer, gregmos/PII-Shield, IngvarConsulting/unica, mrkhachaturov/rkstack (`hooks/session-start`), IA-PieroCV/cc_matrix_channel (`scripts/launcher.ts`). — [gh code search results, 2026-10-01](https://github.com/search?q=CLAUDE_PLUGIN_DATA+releases%2Fdownload&type=code)

**B. Plugin carries no binary and expects the user to install the CLI first**

- **gastownhall/beads** (Go `bd`, Steve Yegge). The plugin manifest wires hooks to bare commands, `"SessionStart": [... "command": "bd prime"]` and the same for `PreCompact`. The plugin directory holds only skills, agents and manifests for Claude, Codex and Copilot. The docs say the `bd` CLI must be installed first "via Homebrew, npm, or script". — [plugin.json](https://github.com/gastownhall/beads/blob/main/plugins/beads/.claude-plugin/plugin.json), [Beads Claude Code plugin docs](https://beads.gascity.com/integrations/claude-code-plugin)
- **cameronsjo/cadence-hooks** (Rust). One binary implements 78 hooks for 6 plugins, which the README pitches as having "sub-millisecond cold starts and zero runtime dependencies". You install it through Homebrew tap, Scoop/WinGet, `cargo install --git`, or by hand from release archives (`macos-aarch64`, `macos-x86_64`, `linux-x86_64`, `linux-aarch64`, `windows-x86_64`). The plugins call it through `.sh` wrappers, and the README warns: "Git Bash is required for the hooks to fire … Claude Code runs shell-form hook commands via Git Bash on Windows (falling back to PowerShell, which can't run `.sh`, when Git Bash is absent)". — [README](https://github.com/cameronsjo/cadence-hooks)
- **Anthropic's official LSP plugins** (`rust-analyzer-lsp`, `gopls-lsp` and others in anthropics/claude-plugins-official) ship only config. The README tells users to install the binary themselves with `rustup component add rust-analyzer`, brew, apt/pacman, or a manual release download. — [rust-analyzer-lsp README](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/rust-analyzer-lsp)
- Search also returned other Rust hook-binary repos that build from source or expect a manual install: soundslocke/claude-hooks, ticpu/ticpu-claude-command-hook (runs from `target/release/`), and oguzsh/claudey (README: "built from source via `bash bin/setup.sh`, not checked into git"). — [web search results](https://github.com/oguzsh/claudey), [ticpu](https://github.com/ticpu/ticpu-claude-command-hook), [soundslocke](https://github.com/soundslocke/claude-hooks)

**C. Plugin's executables in `bin/` placed on PATH**
- `bin/dx-done` from `claude-dx-done` is cited in a Claude Code issue as an example of a plugin that ships a bare command through `bin/`. — [anthropics/claude-code#68894](https://github.com/anthropics/claude-code/issues/68894)

### Inferences
- In the launcher-based plugins, the strongest choices are: version pinned to `plugin.json` (mcp-file-tools, cortexdb, claude-code-notification), a SHA-256 check against GoReleaser's `checksums.txt` (mcp-file-tools only, among those I read), atomic tmp+rename, an env-var override for a local binary (cortexdb `CORTEXDB_MCP_BIN`, crw `CRW_MCP_BINARY`), and stderr-only logging so stdout stays clean for MCP stdio.
- Windows is the weak spot. Several launchers are POSIX-only (tricorder, ghx's sh path, claude-code-notification). Those that do cover Windows add a separate `.cmd` or `.exe` launcher, or use Node so one launcher works everywhere.
- None of the launchers I read handles **Linux musl vs glibc**. Go binaries are usually static (CGO off), which makes this moot for Go. Rust projects would need `*-unknown-linux-musl` targets to avoid it.

### Gaps
- I couldn't find a well-known, high-install-count Rust plugin that commits per-platform binaries straight into the plugin repo. The code search showed none. Size and repo-bloat concerns probably explain it, but I found no source saying so.
- I didn't read the hook scripts of claude-code-notification. Its behaviour above comes from RELEASING.md.
- How mcp-file-tools gets its Windows `.exe` launcher onto disk (committed? built at release?) wasn't clear from the directory listing, which shows only the sh launcher under `plugin/launcher/`.

## Q2: How they handle checksums, version skew, offline use, unsupported platforms, first-run hook timeouts, CLAUDE_PLUGIN_DATA, and updates

### Takeaway
The robust design that has emerged: a cache key that includes the plugin version, stored in `${CLAUDE_PLUGIN_DATA}` (which survives updates); a fail-closed checksum check; a fail-open hook (always exit 0 and log); and a clear stderr message on unsupported platforms. Offline first runs still fail in every implementation I read. The MCP case is worse because the client just hangs waiting for `initialize`.

### Cited Findings
- **Checksums:** mcp-file-tools checks SHA-256 against the release's `checksums.txt` in all three launchers and aborts on a mismatch or a missing entry. cortexdb, tricorder and ghx don't verify anything. — [run.js](https://github.com/dimitar-grigorov/mcp-file-tools/blob/main/plugin/bin/run.js), [cortexdb-mcp](https://github.com/liliang-cn/cortexdb/blob/main/plugins/cortexdb/bin/cortexdb-mcp), [tricorder wrapper](https://github.com/tweag/tricorder/blob/main/agent-plugins/tricorder-mcp/servers/tricorder-mcp)
- **Signatures:** none of the plugins I read verifies a signature. In the MCPB toolchain, `mcpb verify` never checks PKCS#7 signatures, because node-forge's `verify()` throws "not yet implemented" and the error is swallowed as "unsigned" (open as of 2026-06). — [modelcontextprotocol/mcpb#260](https://github.com/modelcontextprotocol/mcpb/issues/260)
- **Version skew:** projects take one of three approaches. (a) Pin to `plugin.json`, with the version in the cache filename so an upgrade fetches a new binary automatically: mcp-file-tools, cortexdb (which also deletes stale versions). (b) Pin, plus a CI gate that fails if the tag ≠ `plugin.json`: claude-code-notification. (c) Float to the latest release: tricorder (checks daily), ghx (latest non-plugin tag). — sources as above, plus [RELEASING.md](https://github.com/berk-karaal/claude-code-notification/blob/main/RELEASING.md)
- **Offline / restricted network:** tricorder falls back to the cached binary when the network fails. On a cold cache, crw-mcp's npm launcher on Windows "cannot start at all" behind a restricted network. GitHub release downloads gave ECONNRESET/ETIMEDOUT while `api.github.com` worked, and "the MCP client then hangs waiting for `initialize` (no stdout at all), so the server just looks 'broken' rather than 'offline'" (fastcrw/crw#597, 2026-09-30, closed). — [fastcrw/crw#597](https://github.com/fastcrw/crw/issues/597)
- **Unsupported platforms:** every launcher I read exits non-zero with a stderr message naming the OS/arch. tricorder also tells users how to build from source and point the MCP command at the result. — [tricorder wrapper](https://github.com/tweag/tricorder/blob/main/agent-plugins/tricorder-mcp/servers/tricorder-mcp)
- **Hook timeouts / first run:** claude-code-notification downloads in a `SessionStart` hook that "always exits 0", and later hooks re-check the version before dispatching. — [RELEASING.md](https://github.com/berk-karaal/claude-code-notification/blob/main/RELEASING.md)
- **CLAUDE_PLUGIN_DATA:** the docs define it as `~/.claude/plugins/data/<id>/`, "created on first reference and kept across plugin updates", and deleted on uninstall from the last scope unless `--keep-data` is passed. It's exported to hook processes, MCP stdio servers and LSP servers, but it isn't present in the Bash tool environment. — [Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference)
- **Updates:** `${CLAUDE_PLUGIN_ROOT}` is `cache/<marketplace>/<plugin>/<version>/` and moves with every version. Old version directories get an `.orphaned_at` marker and are removed 14 days later. "When a copied plugin updates mid-session, hook commands, monitors, MCP servers, and LSP servers keep using the previous version's path" until `/reload-plugins`. A manifest that pins `"version"` keeps users on the cached copy until the string changes. — [Plugin loading reference](https://code.claude.com/docs/en/plugins/loading)
- Claude Code's own automatic dependency install, which covers Node `package.json` only, runs with `--ignore-scripts` and has a 60-second timeout. The docs tell plugin authors to install anything else (packages that need lifecycle scripts, Python deps and so on) "from a hook into the persistent data directory". — [Plugin loading reference](https://code.claude.com/docs/en/plugins/loading)

### Inferences
- Keying the cache on `plugin.json`'s version under `${CLAUDE_PLUGIN_DATA}` fits Claude Code's update model. Because the old ROOT is kept for 14 days, a session still running the old version keeps working, and the new version fetches its own binary.
- MCP launchers should time-box the download and print a clear stderr error. Otherwise an offline machine looks like a hung server (crw#597).

### Gaps
- I didn't confirm the current default hook timeout or whether a `SessionStart` hook's duration blocks the session. Check the [hooks reference](https://code.claude.com/docs/en/hooks).
- No real-world report turned up of a first-run download timing out inside a hook.

## Q3: What Anthropic's documentation recommends for plugins that need executables

### Takeaway
The docs offer three paths. Use `${CLAUDE_PLUGIN_ROOT}` to reference bundled binaries from hooks, MCP and LSP configs. Install runtime dependencies from a hook into `${CLAUDE_PLUGIN_DATA}`. Use plugin `bin/` only to put bare commands on the Bash tool's PATH. **claude.ai org sync and Cowork reject any plugin that has a top-level `bin/`.** Their stated alternative is to put executables in `scripts/` and reference them as `${CLAUDE_PLUGIN_ROOT}/scripts/<name>`. The manifest's `mcpServers` field also accepts `.mcpb`/`.dxt` bundles by path or by https URL.

### Cited Findings
- Standard layout row for `bin/`: "Files here are on the Bash tool's `PATH` while the plugin is enabled, so Claude runs them as bare commands. claude.ai and Cowork don't install a plugin that has this directory." — [Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference)
- Org sync: "Don't include a top-level `bin/` directory … claude.ai rejects a plugin that has one … The error message starts with `Plugin contains a top-level bin/ directory` … Keep executables in another directory, such as `scripts/`, and reference them as `${CLAUDE_PLUGIN_ROOT}/scripts/<name>`." — [Sync your organization's plugins](https://claude.com/docs/plugins/org-sync)
- `${CLAUDE_PLUGIN_ROOT}` is described as for "Scripts, binaries, and config files bundled with the plugin", and `${CLAUDE_PLUGIN_DATA}` as for "Installed dependencies such as `node_modules`, generated code, and caches". — [Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference)
- `mcpServers` accepts a `.mcpb`/`.dxt` path: Claude Code "Extracts the `.mcpb` or `.dxt` bundle into `.mcpb-cache/` under the plugin root". It also accepts an `https://…/server.mcpb` URL, which it "Downloads … into `.mcpb-cache/`". Bundles declared by project-scope plugins are skipped. — [Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference), [Plugin loading reference](https://code.claude.com/docs/en/plugins/loading)
- The docs recommend exec-form hooks (`args`) so that each path stays a single argument, and they say double-quote `"${CLAUDE_PLUGIN_ROOT}"` in shell form. `claude plugin validate` warns about unquoted variables. "On Windows, the substituted paths use forward slashes." — [Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference)
- Marketplace plugins are copied into `cache/…/<version>/`. "Files outside the plugin directory aren't copied." — [Plugin loading reference](https://code.claude.com/docs/en/plugins/loading)
- A plugin `bin/` reaches the PATH only through the Bash tool's shell snapshot. Bugs reported in 2026: PowerShell tool subprocesses didn't get plugin `bin/` (#68894, closed 2026-06-16). A truncated shell snapshot silently dropped `bin/` PATH entries (#68066, closed 2026-07-25). `<plugin>/bin` was added for every enabled plugin with no existence check, which pushed the inlined snapshot past Windows' 8191-character command-line limit and broke every Bash call (#95653, Claude Code 2.1.278, closed 2026-09-25). — [#68894](https://github.com/anthropics/claude-code/issues/68894), [#68066](https://github.com/anthropics/claude-code/issues/68066), [#95653](https://github.com/anthropics/claude-code/issues/95653)
- An open feature request asks to expose `${CLAUDE_PLUGIN_VERSION}` to skills (2026-09-26). Today launchers parse `plugin.json` themselves to get the version. — [#97476](https://github.com/anthropics/claude-code/issues/97476)

### Inferences
- If the plugin must also work on claude.ai and Cowork, binaries and launchers belong under something like `scripts/` or `libexec/`, not `bin/`. cortexdb's layout would be rejected there.
- Plugin `bin/` has been fragile on Windows through mid-to-late 2026. Hooks and MCP configs that use an absolute `${CLAUDE_PLUGIN_ROOT}/...` path don't depend on that PATH plumbing.

### Gaps
- I found no Anthropic doc that states a plugin size limit, or that says whether the executable bit survives the copy into `cache/`.

## Q4: How Rust and Go MCP server authors distribute for Claude, and the failure modes reported

### Takeaway
The common channels are an npm wrapper with per-platform `optionalDependencies` packages (Azure/Microsoft MCP), npm launchers that download the binary from GitHub on first run (crw-mcp), Docker, and `.mcpb` bundles with `server.type: "binary"`. Each has documented failure modes: `npx.cmd` can't be spawned directly on Windows, optionalDependencies get skipped, a wrapper's auto-install wrote into the user's package.json, restricted networks block release downloads, and MCPB loses Unix modes on extraction or fails to launch.

### Cited Findings
- The MCPB manifest supports `server.type: "binary"`, described as "Pre-compiled executable with all dependencies included". `mcp_config.platform_overrides` is keyed by `win32`/`darwin`/`linux`, and `compatibility.platforms` follows Node's `process.platform`. "For binaries, apps will automatically append .exe on Windows." `${__dirname}` resolves to the extension directory. — [MCPB MANIFEST.md](https://github.com/modelcontextprotocol/mcpb/blob/main/MANIFEST.md)
- MCPB failure: "Claude Desktop's extension extraction path writes **every** unpacked file at mode `0600`, discarding the Unix permission bits stored in the `.mcpb` ZIP's `external_attr`", so `type: binary` servers fail with EACCES. Observed on Claude Desktop 1.21459.3 / macOS 15.7.7 with Flexibits' Fantastical extension (#294, open, 2026-07-16). Related issues: #209 (merged; `mcpb pack` forces `|0o111` on binary entry points), #235 (open; `mcpb pack` on Windows omits Unix permission metadata), #282 (open; an unpacked `type: binary` extension is never launched, ENOENT). — [mcpb#294](https://github.com/modelcontextprotocol/mcpb/issues/294), [mcpb#282](https://github.com/modelcontextprotocol/mcpb/issues/282)
- MCPB signing: `mcpb sign` produces bundles that strict zip parsers reject, "including Claude Desktop itself ('Invalid comment length')" (#278), and verification doesn't work at all (#260). — [mcpb#278](https://github.com/modelcontextprotocol/mcpb/issues/278), [mcpb#260](https://github.com/modelcontextprotocol/mcpb/issues/260)
- A Claude Code issue reports that installing a `.mcpb` was a silent no-op on Claude Desktop 1.12603.1 (macOS), while the identical binary worked when configured by hand (2026-06-13, closed). — [anthropics/claude-code#68240](https://github.com/anthropics/claude-code/issues/68240)
- npm per-platform packages: Azure/Microsoft MCP uses a wrapper with `optionalDependencies` on packages such as `@azure/mcp-win32-x64` and `@azure/mcp-darwin-arm64`. When the platform package is missing, the wrapper runs a bare `npm install <pkg>` in the inherited cwd, which **saved `@azure/mcp-<platform>` into the user's project package.json and lockfile** (PR #3184, 2026-07-30). — [microsoft/mcp#3184](https://github.com/microsoft/mcp/pull/3184), [azure-mcp npm README](https://github.com/azure/azure-mcp/blob/main/eng/npm/README.md)
- npm skips optionalDependencies whose `engines` don't match the running Node version, and crw's Windows platform packages were unavailable on npm, so on win32 the launcher always fell back to a GitHub download. (The search summary attributes both claims to crw#597. The issue body I read confirms that win32 "always takes the download path".) — [fastcrw/crw#597](https://github.com/fastcrw/crw/issues/597)
- Windows `npx`: "`npx` is installed as `npx.cmd` … `child_process.spawn()` — used by Claude Desktop and Claude Code — cannot execute `.cmd` files unless `shell: true`". The workaround is `"command": "cmd", "args": ["/c", "npx", …]` (modelcontextprotocol/servers#3460, open, 2026-03-03). — [servers#3460](https://github.com/modelcontextprotocol/servers/issues/3460)
- mcp-file-tools picked a Node launcher partly to avoid "bash resolves to WSL" when Claude Code spawns a server without a shell on Windows (code comment). cadence-hooks says `.sh` hooks need Git Bash on Windows (README). — [run.js](https://github.com/dimitar-grigorov/mcp-file-tools/blob/main/plugin/bin/run.js), [cadence-hooks](https://github.com/cameronsjo/cadence-hooks)
- Background on packaging Rust for npm with per-platform packages: [Orhun's blog](https://blog.orhun.dev/packaging-rust-for-npm/), [Sentry engineering](https://sentry.engineering/blog/publishing-binaries-on-npm).

### Inferences
- In a Claude Code plugin, `"command": "node"` pointing at a launcher in the plugin avoids the `npx.cmd` spawn problem and npm cold starts, because `node.exe` is a real executable. It still requires Node on PATH. Claude Code's native installer doesn't guarantee Node, though the npm install of Claude Code does imply it.
- A direct `command` pointing at a POSIX sh script is unreliable on Windows when there's no shell. Pair it with a `.cmd` file, or use an `.exe` shim or a Node launcher.

### Gaps
- I didn't measure npx cold-start latency and found no quantified reports of it.
- I didn't find a uvx-distributed Rust or Go MCP server that is specifically packaged as a Claude plugin (maturin-style wheels).

## Q5: GitHub issues on shipping binaries, size limits, permissions, Gatekeeper and SmartScreen

### Takeaway
The reported problems center on plugin `bin/` PATH plumbing (especially on Windows) and on MCPB permission bits. The executable bit being lost is confirmed for MCPB extraction in Claude Desktop. I found nothing for marketplace plugins in Claude Code. I found no issue specifically about macOS Gatekeeper quarantine or Windows SmartScreen/Defender for plugin binaries.

### Cited Findings
- Issues about plugin `bin/` on PATH: #68894 (PowerShell tool), #68066 (snapshot truncation), #81356 ("Shell snapshot PATH export contains only the plugin bin dir, system directories lost", 2.1.204, closed), #95653 (dead PATH entries and the 8191-character Windows limit), #72728 and #81732 (Git Bash snapshot PATH handling on Windows, open). — [#81356](https://github.com/anthropics/claude-code/issues/81356), [#72728](https://github.com/anthropics/claude-code/issues/72728), [#81732](https://github.com/anthropics/claude-code/issues/81732), [#95653](https://github.com/anthropics/claude-code/issues/95653)
- #42872 (2026-04-03, closed): "[DOCS] Plugin docs missing `bin/` executables and Bash bare-command usage". According to #68894, `bin/` PATH support arrived in v2.1.91. — [#42872](https://github.com/anthropics/claude-code/issues/42872), [#68894](https://github.com/anthropics/claude-code/issues/68894)
- Plugin variable resolution: `CLAUDE_PLUGIN_ROOT` is unset in the agent Bash env, and still points at the source dir in hooks, for string-source local marketplace plugins (#93057, open). The CLI and the desktop app resolve different plugin identities (`<p>@<p>` vs `<p>@inline`), so the desktop app's MCP server gets empty `userConfig` values (#92427, open). — [#93057](https://github.com/anthropics/claude-code/issues/93057), [#92427](https://github.com/anthropics/claude-code/issues/92427)

Earlier pack-side permission issues: mcpb #12, #14, #57, #235 (cited in #294). There's also an older "Access denied when attempt to run a mcp server via binary" report (mcpb#42, 2025-07-03, closed). — [mcpb#42](https://github.com/modelcontextprotocol/mcpb/issues/42)
- Windows: #66540 (open) reports terminal/cmd windows flashing on every subprocess spawn. — [#66540](https://github.com/anthropics/claude-code/issues/66540)

### Inferences
- Launchers that download to `${CLAUDE_PLUGIN_DATA}` and `chmod 755` before an atomic rename don't depend on zip or cache permission preservation at all. That's likely part of why the download pattern dominates over committing binaries.
- Binaries fetched with curl or Node `fetch` don't get the `com.apple.quarantine` xattr (only browser-style downloaders set it), so Gatekeeper is less of an issue for downloaded binaries than for bundled ones. This is from general macOS knowledge. I found no source specific to plugins.

### Gaps
- I found no anthropics/claude-code issue about plugin size limits, lost chmod +x in marketplace plugins, Gatekeeper quarantine, or SmartScreen/Defender blocking plugin binaries. Keyword search on the GitHub issues returned nothing for these, which may be a limit of search coverage rather than proof that no such issues exist.
