# Ship the binary, resolve it locally, download last

Node.js is guaranteed to plugin hooks on exactly one Claude Code surface, Claude Code on the web, and that surface does not install plugins from repo or user settings. Everywhere else `node` is present only because the user installed it: the native-installer CLI embeds Bun but exposes no runtime, the npm CLI has used the same native binary since v2.1.198, and the Desktop Code tab runs on the host OS with the user's PATH. Cowork hooks run under `sh -c` in a Linux workspace (a cloud container by default, and the only option for new tasks from 2026-10-06) where Node 22 is very likely present but no document promises it. Across npm, VS Code, PyPI, cargo and Claude plugins, the designs that hold up put the right binary on disk at install time, through per-platform packages the package manager selects, and keep a runtime download or source build only as a fallback, because first-run downloads fail offline, behind proxies, and silently inside short-lived hooks. The temper proposal is sound in its core: per-platform npm packages pinned in the plugin's lockfile ride on Claude Code's own dependency install, which runs with `--ignore-scripts` and still works for `optionalDependencies`. Four parts need to change. cargo-dist's npm installer is the wrong tool, because it downloads on first run with no checksum. The `cargo build` fallback cannot run inside a synchronous hook. The Linux packages must not declare `libc`. An enforcement plugin must not fail silently the way Weigh-In's ledger hooks do. Weigh-In bundles its binaries in the release zip and needs no Node, npm or network. That suits a zip uploaded to claude.ai, but a git marketplace cannot carry it without committing binaries, and its `sh` hooks fail on Windows machines without Git Bash.

## Node is guaranteed on one surface, and plugin hooks rarely reach it

The hooks reference documents only the shell: shell-form hooks run under "`sh -c` on macOS and Linux, Git Bash on Windows, or PowerShell when Git Bash isn't installed", and exec form (`command` plus `args`) spawns the executable directly with no shell. The docs use `node` in examples, noting that the `node`-plus-script pattern "works on every platform because `node.exe` is a real binary", but they never say Node is installed ([Hooks reference](https://code.claude.com/docs/en/hooks)). The system requirements list no Node prerequisite, and **"The installed `claude` binary does not itself invoke Node"**. Node 22+ is needed only to run `npm install` for the npm package, which "downloads a native binary that doesn't use your Node.js at runtime" ([Advanced setup](https://code.claude.com/docs/en/setup)). The native binary embeds Bun, but the `BUN_BE_BUN=1` escape hatch that exposed it stopped working in 2.1.35 ([#24575](https://github.com/anthropics/claude-code/issues/24575)), and the request for a guaranteed hook runtime was closed as not planned ([#30465](https://github.com/anthropics/claude-code/issues/30465)). Anthropic's own behaviour is the strongest signal. **Not one `hooks.json` in anthropics/claude-plugins-official calls `node`**: they use `sh`, `bash` and `python3`, and `claude-security` probes for python3 and emits a `systemMessage` when it is missing ([claude-plugins-official](https://github.com/anthropics/claude-plugins-official); [claude-security hooks.sh](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/claude-security/hooks/hooks.sh)).

| Surface | Hook shell | Node for hooks | Evidence |
|---|---|---|---|
| CLI, native installer (Anthropic's recommended install) | `sh -c`; Git Bash or PowerShell on Windows | Only if the user installed it | [Advanced setup](https://code.claude.com/docs/en/setup) |
| CLI, npm package | Same | Very likely, since npm needed Node 22+, but the version manager's PATH can differ from the hook's | [Advanced setup](https://code.claude.com/docs/en/setup) |
| Desktop Code tab | Same, on the host OS | Only if installed and on the app's PATH. macOS reads the shell profile; Windows inherits the environment without PowerShell profiles. The Electron app's bundled Node is not exposed | [Desktop docs](https://code.claude.com/docs/en/desktop) |
| Claude Code on the web | `sh -c`, Ubuntu 24.04 x86_64 | **Documented**: Node 22 on PATH, with npm, Rust and cargo | [Cloud environments](https://code.claude.com/docs/en/cloud-environments) |
| Cowork (cloud default from 2026-10-06) | `sh -c`, Linux, native ELF Claude Code | **Likely, undocumented** | [Cowork changelog](https://claude.com/docs/cowork/changelog); [pvieito.com](https://pvieito.com/2026/01/inside-claude-cowork) |

Claude Code on the web is a near-empty target for plugins: a cloud session "doesn't install the plugins a repository turns on under `enabledPlugins`", nor plugins enabled only in user settings. Only hooks committed in the repo's `.claude/settings.json` and server-managed hooks run there ([Cloud environments](https://code.claude.com/docs/en/cloud-environments)).

Cowork is the surface that matters most for the question, and it rests on indirect evidence. Plugin hooks "Load" in Cowork. Plugins with a top-level `bin/` "Can't be installed" ([Platform support](https://claude.com/docs/plugins/platform-support)). Synced plugins are downloaded "into the session's own environment when the session starts" ([Plugin loading](https://code.claude.com/docs/en/plugins/loading)). New tasks run only in the cloud from **2026-10-06** ([Get started with Cowork](https://support.claude.com/en/articles/13345190-get-started-with-claude-cowork)), in a container that reports `CLAUDE_CODE_ENTRYPOINT=remote_cowork` and `CLAUDE_CODE_REMOTE_ENVIRONMENT_TYPE=cloud_default` and sends egress through a gateway ([#88989](https://github.com/anthropics/claude-code/issues/88989)). Two facts point to Node. A January 2026 inspection of the then-local VM found Ubuntu 22.04 on **aarch64** with Node 22.22.0, Claude Code as a native ELF at `/usr/local/bin/claude`, and a proxy allowlist that included `registry.npmjs.org` ([pvieito.com](https://pvieito.com/2026/01/inside-claude-cowork)). The 2026-09-17 Cowork changelog then "Fixed preinstalled Node.js packages such as `pptxgenjs`, `docx`, `pdf-lib` and `sharp` not being found by `require()`" ([Cowork changelog](https://claude.com/docs/cowork/changelog)). Preinstalled Node packages imply a preinstalled Node. Three things stay unknown: the cloud image's architecture (the old local VM was aarch64, while Claude Code on the web is x86_64), whether GitHub downloads get through (an open issue reports that "Cowork cloud sessions cannot access any GitHub repository", [#84581](https://github.com/anthropics/claude-code/issues/84581)), and whether `${CLAUDE_PLUGIN_DATA}` survives between sessions. Treat Cowork's `node` as observed behaviour that one probe can confirm, not as a contract.

On Windows, a shell-form hook that starts with `sh` breaks wherever Git for Windows is missing, because Claude Code then falls back to PowerShell ([Advanced setup](https://code.claude.com/docs/en/setup)). Exec form needs a real `.exe`, not a `.cmd` shim ([Hooks reference](https://code.claude.com/docs/en/hooks)). `node.exe` qualifies, which is why temper's existing exec-form `node` hooks are the Windows-safe choice once Node is present.

## Mature ecosystems put the binary on disk at install time and keep downloading as a fallback

The npm ecosystem has already run this experiment. esbuild 0.13.0 (2021) abandoned its postinstall download because it broke under `npm --ignore-scripts`. It moved to listing every platform package as an optional dependency and letting the package manager install only the matching one, "a built-in part of the package manager" ([esbuild v0.13.0](https://github.com/evanw/esbuild/releases/tag/v0.13.0)). Its installer comments explain that manual downloading "has a lot of obscure edge cases that fail because people have customized their environment in some strange way". It also runs the binary with `--version` at install to catch skew ([node-install.ts](https://raw.githubusercontent.com/evanw/esbuild/main/lib/npm/node-install.ts)). Sentry reached the same design and keeps a postinstall download only as a backstop, because "we haven't found a reliable way to ship binaries if both optionalDependencies and postinstall scripts are disabled" ([Sentry blog](https://blog.sentry.io/publishing-binaries-on-npm)). Biome's launcher maps `process.platform` × `process.arch` to `@biomejs/cli-*`, detects musl by running `ldd --version`, honours a `BIOME_BINARY` override, and exits 1 with a message when nothing matches ([Biome launcher](https://raw.githubusercontent.com/biomejs/biome/main/packages/@biomejs/biome/bin/biome)). napi-rs pins platform packages to exact versions and declares `os`, `cpu` and `libc` on each ([napi-rs release docs](https://napi.rs/docs/deep-dive/release)). The pattern's known hazard was npm recording only the current platform's optional package when a lockfile was regenerated, so a colleague on another architecture silently got no binary. **That was fixed in npm 11.3.0** (April 2025) ([npm/cli #4828](https://github.com/npm/cli/issues/4828); [PR #8184](https://github.com/npm/cli/pull/8184)). The other failures are users who set `--omit=optional` or Yarn `ignore-optional` ([sentry-cli #1862](https://github.com/getsentry/sentry-cli/issues/1862)).

cargo-dist's npm installer goes the other way. As of v0.33.0 (2026-09-11) it is one package that fetches the platform archive from the release URL at postinstall, and again on first run if the binary is missing (`!this.exists() ? this.install(true) : …`). It uses only `artifactDownloadUrls[0]` ("FIXME: implement NPM installer handling of fallback download URLs"), and checksum verification is "Not implemented" ([binary-install.js](https://raw.githubusercontent.com/axodotdev/cargo-dist/main/cargo-dist/templates/installer/npm/binary-install.js); [binary.js](https://raw.githubusercontent.com/axodotdev/cargo-dist/main/cargo-dist/templates/installer/npm/binary.js); [releases](https://github.com/axodotdev/cargo-dist/releases)). It is the failure profile esbuild left behind in 2021. The rest of dist is useful. It writes a `.sha256` per archive by default, builds Linux gnu and musl, macOS and Windows targets, and has experimental GitHub attestations ([dist config](https://axodotdev.github.io/cargo-dist/book/reference/config.html)). The research found no authoritative source on cargo-npm, so this report makes no claim about it beyond that.

The other ecosystems agree. VS Code publishes one VSIX per target, with `alpine-*` as the musl targets and an untargeted VSIX as the fallback for every other platform ([VS Code publishing](https://code.visualstudio.com/api/working-with-extensions/publishing-extension#platformspecific-extensions)). rust-analyzer moved in December 2021 "to bundle the server binary with the extension, instead of downloading it on the first load" ([changelog #109](https://rust-analyzer.github.io/thisweek/2021/12/27/changelog-109.html)). It keeps a `no-server` VSIX plus `server.path` for unsupported platforms ([rust-analyzer book](https://rust-analyzer.github.io/book/vs_code.html)). clangd's download-on-activation shows what happens otherwise: failures on offline remote hosts, reinstall loops, no Apple M1 support, repeated prompts ([vscode-clangd #112](https://github.com/clangd/vscode-clangd/issues/112); [#194](https://github.com/clangd/vscode-clangd/issues/194)). ruff-vscode has the cleanest resolution order: a user path list first, then `fromEnvironment` falling back to the bundled binary, with a minimum-version check that warns and degrades ([Ruff settings](https://docs.astral.sh/ruff/editors/settings/)). Python wheels let the installer pick among `musllinux_1_2`, `manylinux_2_17`, macOS and Windows `py3-none-*` tags, and `uvx` adds pinned, cached one-shot runs ([PyPI ruff](https://pypi.org/project/ruff/#files); [uv tools](https://docs.astral.sh/uv/guides/tools/)). `gh extension install` matches a fixed `OS-ARCH[.exe]` suffix, falls back to amd64 under Rosetta, and on no match prints an error that suggests filing an issue. It verifies nothing ([manager.go](https://raw.githubusercontent.com/cli/cli/trunk/pkg/cmd/extension/manager.go)). cargo-binstall resolves assets from `[package.metadata.binstall]` templates or default names such as `{ name }-{ target }-v{ version }{ archive-suffix }`, verifies minisign signatures, and falls back to QuickInstall and then a source build ([SUPPORT.md](https://raw.githubusercontent.com/cargo-bins/cargo-binstall/main/SUPPORT.md); [SIGNING.md](https://github.com/cargo-bins/cargo-binstall/blob/main/SIGNING.md)). Zed is the exception that proves the rule: its WASM extensions cannot ship binaries, so they download through capability-gated host APIs that users can revoke ([Zed capabilities](https://zed.dev/docs/extensions/capabilities)).

Claude plugins have mostly not learned this yet. The dominant pattern is a launcher that reads the version from `plugin.json`, downloads the matching GitHub release asset into `${CLAUDE_PLUGIN_DATA}`, and `exec`s it. Of the launchers read, only mcp-file-tools checks SHA-256 against `checksums.txt`, and it writes atomically with a tmp file and rename ([run.js](https://github.com/dimitar-grigorov/mcp-file-tools/blob/main/plugin/bin/run.js)). cortexdb, tricorder and ghx verify nothing, and tricorder and ghx float to the latest release instead of pinning ([cortexdb-mcp](https://github.com/liliang-cn/cortexdb/blob/main/plugins/cortexdb/bin/cortexdb-mcp); [tricorder wrapper](https://github.com/tweag/tricorder/blob/main/agent-plugins/tricorder-mcp/servers/tricorder-mcp)). claude-code-notification downloads in a `SessionStart` hook that "always exits 0" and re-checks the version before each dispatch ([RELEASING.md](https://github.com/berk-karaal/claude-code-notification/blob/main/RELEASING.md)). The failure that keeps recurring is the cold, offline first run. crw-mcp's launcher could not reach GitHub release downloads on a restricted network, and "the MCP client then hangs waiting for `initialize`", so the server "just looks 'broken' rather than 'offline'" ([fastcrw/crw#597](https://github.com/fastcrw/crw/issues/597)). The same report found npm skipping optional packages whose `engines` did not match. None of the launchers handles musl versus glibc, and Windows is consistently the weak spot. Anthropic's own LSP plugins and Rust hook projects such as cadence-hooks avoid the question by requiring the user to install the binary ([rust-analyzer-lsp](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/rust-analyzer-lsp); [cadence-hooks](https://github.com/cameronsjo/cadence-hooks)).

| Concern | What works | What fails |
|---|---|---|
| Install vs first run | The package manager or extension store installs the matching binary (esbuild, VS Code, wheels) | First-run download inside a short-lived process (clangd, crw-mcp, dist's npm `run()`) |
| Integrity | npm lockfile `integrity` plus Sigstore provenance via trusted publishing ([npm provenance](https://docs.npmjs.com/generating-provenance-statements)); a pinned SHA-256 for any download path | TLS-only downloads (dist npm, cortexdb, gh) |
| Offline | Bundled binary or npm/registry cache | Any cold-cache download |
| Version skew | Exact-version pins, an install-time `--version` check, a cache keyed on plugin version | Floating "latest" (tricorder, ghx) |
| Unsupported platform | A clear message naming OS and arch, an override path, a source build | Silent no-op or a hang |
| Windows | Exec form with a real `.exe` (`node.exe`, or the binary itself) | `sh` launchers without Git Bash; `npx.cmd` without a shell ([servers#3460](https://github.com/modelcontextprotocol/servers/issues/3460)) |

## Claude Code's own npm step makes the proposal work in the CLI, with four holes

The proposal's key move is to put `@scope/temper-<platform>` packages in the plugin's `package.json` and `package-lock.json` and let Claude Code install them. That rests on documented behaviour. When Claude Code copies a plugin into its cache it installs npm or Bun dependencies from a committed lockfile, "runs the matched lockfile's package manager from the user's PATH", uses `--ignore-scripts`, allows registry dependencies only, and has a 60 s timeout. **"A failed or skipped install never blocks the plugin"** ([Plugin loading](https://code.claude.com/docs/en/plugins/loading)). Because `optionalDependencies` selection needs no install scripts, the esbuild mechanism survives `--ignore-scripts` intact, while dist's postinstall never runs at all. The npm path also inherits the lockfile's SHA-512 `integrity` and npm provenance for every platform package for free ([npm provenance](https://docs.npmjs.com/generating-provenance-statements)). The node launcher costs little relative to temper today. Bare Node startup is about 20 ms on Node 20 and 27.5 ms on Node 22 ([nodejs/performance #180](https://github.com/nodejs/performance/issues/180)), and temper's hooks already pay that on every call because `scripts/temper.mjs` is a Node program. Moving the logic into Rust adds one child spawn and removes the JS work.

The holes are specific. **First**, the auto-install "does not run for plugins loaded in place, such as `--plugin-dir` or a local-directory marketplace" ([Plugin loading](https://code.claude.com/docs/en/plugins/loading)). Temper's own development loop and any local-marketplace install, which is how Weigh-In ships today ([D-0006](https://github.com/Wet-Ink-Corporation/weigh-in/blob/main/docs/decisions/build-decisions.md#d-0006)), get no `node_modules` and need the fallback. Whether claude.ai-synced plugins in Cowork get the install is undocumented. **Second**, a failed install is silent, and npm installs only what `os` and `cpu` allow. A Windows-on-ARM machine will not receive a `win32-x64` package, and if the musl packages declare `libc: ["musl"]` (as napi-rs does for its musl builds) glibc hosts will skip the only Linux binary. Static musl builds run on glibc hosts, which is why dist falls back to "static musl" when glibc is too old ([binary.js](https://raw.githubusercontent.com/axodotdev/cargo-dist/main/cargo-dist/templates/installer/npm/binary.js)), so the Linux packages should set `os` and `cpu` and omit `libc`. **Third**, `cargo build --release` takes minutes, while temper's `UserPromptSubmit` and `PreToolUse` hooks allow 15–30 s, and the documented default is only 30 s on `UserPromptSubmit` ([Hooks reference](https://code.claude.com/docs/en/hooks)). The build must run where no timeout applies: an `async: true` hook (whose timeout "is not enforced", per the same page), or `/temper:setup`. The hot-path hooks only look for its output. **Fourth**, per-platform packages must live on a registry every user can read without credentials. If temper stays internal, as Weigh-In is ([D-0007](https://github.com/Wet-Ink-Corporation/weigh-in/blob/main/docs/decisions/build-decisions.md#d-0007)), public npm exposes the binaries and a private registry breaks the anonymous auto-install.

The users' CI half of the proposal is the strongest part. Replacing the 279 KB of vendored JS that `/temper:setup` copies into `.claude/temper/` with a pinned `cargo binstall` (or `cargo install --locked` as the slow fallback) makes CI run the same binary the hooks run. It also removes a vendored artifact that drifts from the plugin. binstall works out of the box if the release assets follow its default naming, and minisign gives it a signature to check ([SUPPORT.md](https://raw.githubusercontent.com/cargo-bins/cargo-binstall/main/SUPPORT.md)). GitHub attestations (`actions/attest`, `gh attestation verify`) add provenance for anyone who downloads directly ([GitHub artifact attestations](https://docs.github.com/en/actions/security-for-github-actions/using-artifact-attestations/using-artifact-attestations-to-establish-provenance-for-builds)). The research did not establish how binstall authenticates against an internal repository's releases, so an internal temper needs that checked.

## Weigh-In trades portability for zero runtime dependencies

Weigh-In takes the bundling route. The release workflow builds `x86_64-unknown-linux-musl`, `x86_64-pc-windows-msvc` and `aarch64-apple-darwin`, places them under `plugin/libexec/<target>/`, zips the plugin, and publishes the raw binaries with `SHA256SUMS` ([release.yml](https://github.com/Wet-Ink-Corporation/weigh-in/blob/main/.github/workflows/release.yml)). The binaries live in `libexec/` because claude.ai rejects a top-level `bin/` ([B-03](https://github.com/Wet-Ink-Corporation/weigh-in/blob/main/docs/decisions/build-decisions.md#b-03); [org sync](https://claude.com/docs/plugins/org-sync)). Hooks call `sh "${CLAUDE_PLUGIN_ROOT}/libexec/weighin" hook` with a 10 s timeout ([hooks.json](https://github.com/Wet-Ink-Corporation/weigh-in/blob/main/plugin/hooks/hooks.json)). The POSIX launcher maps `uname` to a target, prefers the newer of two builds ([B-05](https://github.com/Wet-Ink-Corporation/weigh-in/blob/main/docs/decisions/build-decisions.md#b-05)), `chmod +x`es if needed, falls back to a `weighin` on PATH, and for `hook` exits 0 when nothing is found ([launcher](https://github.com/Wet-Ink-Corporation/weigh-in/blob/main/plugin/libexec/weighin)). A `.cmd` twin serves direct Windows calls. In Cowork the hooks deliberately write nothing ([B-04](https://github.com/Wet-Ink-Corporation/weigh-in/blob/main/docs/decisions/build-decisions.md#b-04)). The skill fetches the musl binary from the GitHub release through the computer's shell, checks it against a SHA-256 stamped into the zipped skill, and falls back to a copy in a connected folder. That download is dormant while the repository is internal ([D-0003](https://github.com/Wet-Ink-Corporation/weigh-in/blob/main/docs/decisions/build-decisions.md#d-0003); [package-plugin.sh](https://github.com/Wet-Ink-Corporation/weigh-in/blob/main/scripts/package-plugin.sh)).

| | Weigh-In today | temper proposal | Recommended for temper |
|---|---|---|---|
| Binary delivery | Bundled in zip `libexec/<target>/` (about 4.3–4.6 MB each) | npm per-platform packages via Claude Code auto-install | npm packages for marketplace installs; optional bundled zip for claude.ai/Cowork |
| Hook launcher | `sh` shell form | `node` exec form | `node` exec form, resolution-only |
| Needs Node | No | Yes | Yes (no regression: temper needs Node today) |
| Windows without Git Bash | Hooks fail with a non-blocking error | Works | Works |
| Targets | 3 (no Linux arm64, no macOS x64) | 5 | 5, plus Windows arm64 if cheap |
| Network at run time | None in hooks; GitHub in the Cowork skill | None (install-time npm) or GitHub (dist) | None in hooks |
| Integrity | SHA-256 pinned in the skill | Lockfile SHA-512 (dist: none) | Lockfile SHA-512 + npm provenance; SHA-256 + attestations on release assets |
| Missing binary | Silent exit 0 | Unspecified | Exit 0 with one `systemMessage` per session |
| `--plugin-dir` / local marketplace | Works (local build) | Needs fallback | Repo `target/release`, then async build into `${CLAUDE_PLUGIN_DATA}` |

Weigh-In's design is right for Weigh-In. A ledger can lose a capture without harm, its distribution is a local marketplace plus a zip upload, and bundling keeps it free of Node, npm and network. The arm64 and egress gaps this report first raised did not hold up in the 2026-10-01 check below: Cowork's cloud workspace and the computer's shell are both x86_64, which its musl build covers, and public release assets download in both. Its Cowork download is blocked only by the repository being internal (D-0007). Copying its bundling into temper's git marketplace would mean committing about 20–25 MB of binaries per release. Its silent `exit 0` is also wrong for an enforcer: when temper's Stop gate cannot find its binary, the user must be told the gate did not run.

## Recommendation: adopt the npm design, minus dist's installer and the in-hook build

Adopt the proposal's architecture (Rust workspace, five targets, per-platform npm packages pinned in the plugin lockfile, exec-form `node` launcher, `cargo binstall` in users' CI), with the changes below. The launcher should do resolution only, with no network and no build, in this order: `TEMPER_BIN`, then `${CLAUDE_PLUGIN_ROOT}/libexec/<target>/` (present only in a bundled zip), then the npm platform package via `require.resolve`, then the repo's own `target/release` (newest-build-wins, as in Weigh-In's B-05, for `--plugin-dir`), then `${CLAUDE_PLUGIN_DATA}/<version>/`, then `temper` on PATH. It checks the version once per plugin version, records a stamp in `${CLAUDE_PLUGIN_DATA}`, and never checks again on the hot path.

| Proposal item | Change | Reason |
|---|---|---|
| 5 CI targets | Keep. Build Linux as static musl. Add `aarch64-pc-windows-msvc` if a runner is cheap | npm `cpu` blocks the x64 package on arm64 Windows; ruff and VS Code ship win-arm64 |
| Per-platform npm packages | Keep, with exact versions equal to `plugin.json`. Set `os`/`cpu`, **omit `libc`**. Generate the lockfile with npm ≥ 11.3.0 and have CI assert all five entries are present. Publish with trusted publishing | npm/cli #4828; static musl runs on glibc; provenance comes free |
| cargo-dist | Use it, if at all, only for the GitHub release (binstall-named archives, `.sha256`, attestations). **Do not use its npm installer** | First-run download, one URL, no checksum, and its postinstall is skipped under Claude Code's `--ignore-scripts` |
| cargo-npm vs in-house script | Write the in-house script (copy napi-rs's pre-publish model: generate six `package.json`s, publish platform packages first) | No verified track record for cargo-npm was found |
| `node` + tiny launcher | Keep exec form. Resolution only. Fail open with **one `systemMessage` per session** naming the platform and the fix | Windows-safe; matches `claude-security`'s probe-and-warn pattern; an enforcer must not fail silently |
| `cargo build --release` fallback | Run it only from an `async: true` SessionStart hook or `/temper:setup`. Use `--locked --release --target-dir "${CLAUDE_PLUGIN_DATA}/target"` behind a lock file, and copy the result to `${CLAUDE_PLUGIN_DATA}/<version>/` | Synchronous hooks time out in 15–30 s; async hooks have no enforced timeout |
| Users' CI | `cargo binstall temper-cli@<pinned> --no-confirm`, with `cargo install --locked` as the fallback. `/temper:setup` writes the pin and CI snippet instead of vendoring JS | One binary everywhere; no drift |
| Cowork / claude.ai | Defer until the probes run. If wanted, ship a zip with all targets under `libexec/` (never `bin/`), built in the same CI run | Unknown auto-install, arch and egress in cloud Cowork |
| Repository visibility | Decide before building: public npm, or accept no auto-install | Same tension as Weigh-In D-0007 |

Six questions still need an empirical check. **(1)** In cloud Cowork after 2026-10-06: the architecture, `node` and `npm` presence, and registry and GitHub egress. **(2)** Whether hook processes see the same PATH as the Bash tool. **(3)** Whether Claude Code's npm auto-install runs for claude.ai-synced plugins in Cowork, producing `node_modules`. **(4)** Whether `${CLAUDE_PLUGIN_DATA}` persists across Cowork sessions. **(5)** Whether executable bits survive the zip upload and the marketplace cache copy; no source covers either, and Claude Desktop is known to drop them for MCPB ([mcpb#294](https://github.com/modelcontextprotocol/mcpb/issues/294)). **(6)** The size limit for an uploaded plugin (since answered from Cowork's docs: 200 MB uncompressed, 5,000 files). Paste this into a Cowork chat and ask Claude to run it with Bash. It answers (1):

```sh

```

## Probe plugin in Cowork, 2026-10-01

Ryan uploaded `binprobe` 0.0.1 under Customize > Plugins and ran it in a Cowork chat. It depends on `esbuild` 0.28.2, whose lockfile (written by npm 11.16) lists all 26 `@esbuild/<platform>` packages, and runs two SessionStart hooks: shell-form `sh probe.sh` and exec-form `node` with `args`. A local run of `npm ci --ignore-scripts` on Windows installed only `@esbuild/win32-x64`, and that binary ran.

| Check | Cowork result | Evidence |
|---|---|---|
| Where hooks run | x86_64 Linux, `CLAUDE_CODE_ENTRYPOINT=remote_cowork`, `CLAUDE_CODE_REMOTE=true` | both hook logs |
| `node` on the hook's PATH | Yes: `/opt/node22/bin/node` v22.22.0 | both hook logs |
| Exec-form `node` hook with `${CLAUDE_PLUGIN_ROOT}` in `args` | Ran; the variable is substituted in `args` | `node-hook.log` exists, `plugin_root_env=set` |
| Claude Code's npm auto-install | **Did not run**: no `node_modules`, no `@esbuild` package | `node_modules=no esbuild_pkgs=none` |
| Platform binary from npm runs | Not testable: nothing was installed | `esbuild_bin=none` |
| Executable bit kept through upload and sync | Yes | `probe_sh_x=yes` |
| `${CLAUDE_PLUGIN_DATA}` | `/root/.claude/plugins/data/binprobe-synced`; persistence needs a second session | `previous_session=none` on the first run |
| Hook PATH equals Bash tool PATH | Yes | diff identical |

Consequences:

- **Per-platform npm packages do not reach Cowork.** The auto-install does not run for a claude.ai-synced plugin there, although npm is on PATH. In Cowork the binary must come from the plugin zip itself (Weigh-In's `libexec/<target>/` route) or from a hook that downloads it. The npm route remains a Claude Code CLI route for marketplace installs.
- **Bundling holds up**: executable bits survive the upload and the sync, so a binary under `libexec/<target>/` runs without a `chmod`.
- **Exec-form `node` hooks work in Cowork**, so temper's existing hook form is safe there.

What Anthropic's documentation says about each result, checked 2026-10-01:

- **The missing install is the documented behaviour for synced plugins.** The dependency install runs only "when Claude Code copies a plugin into the cache": at install, at update, or at session start for an uncached plugin. A plugin turned on in claude.ai loads as `<name>@synced` "with no marketplace and no install record" from the plugins root's `synced/` directory, and in Cowork "Claude Code downloads them into the session's own environment when the session starts" ([Plugin loading](https://code.claude.com/docs/en/plugins/loading)). No page says synced plugins get the install. The same path applies to synced plugins in a terminal session, so the gap is probably not Cowork-only; that is an inference until a terminal session with the synced probe shows `node_modules=no`.
- **Persistence of `${CLAUDE_PLUGIN_DATA}` in Cowork is undocumented.** The Claude Code docs say the data directory is "kept across updates" and deleted on uninstall ([Plugin loading](https://code.claude.com/docs/en/plugins/loading)). Cowork's docs say only that "Claude's work runs on Anthropic's servers, in an isolated environment, and your sessions and files are saved to your Claude account" ([Get started with Cowork](https://support.claude.com/en/articles/13345190-get-started-with-claude-cowork)). Neither confirms nor rules out persistence; a second `/binprobe` session is the only evidence. A download-to-cache fallback would download every session only if it does not persist.
- **Executable bits** are not covered by any page; the result above is observation only.
- **Size is documented**, closing question (6): "Plugin package size (uncompressed): 200 MB" and "Files per plugin package: 5,000" ([Install plugins in Cowork](https://claude.com/docs/cowork/guide/plugins); [Platform support](https://claude.com/docs/plugins/platform-support)). Five bundled targets of about 5 MB each fit easily.
- **Local MCP servers** load in Cowork only "when the Cowork session runs on your computer" ([Platform support](https://claude.com/docs/plugins/platform-support)). With new tasks cloud-only from 2026-10-06, a binary served as a local MCP server does not run in new Cowork tasks; hooks and skills do.
- **Variable substitution in synced skills has been unreliable**: the Cowork changelog fixed "plugin skills that reference `${CLAUDE_PLUGIN_ROOT}` or `${CLAUDE_SKILL_DIR}` sometimes running their commands with those paths blank" ([Cowork changelog](https://claude.com/docs/cowork/changelog)). Hooks received the variables in this probe; skills should not depend on them alone.

## Conclusion

The real decision is not npm versus cargo-dist. It is where the binary comes from at the moment a hook fires, and the evidence says it must already be on disk. Claude Code's own `--ignore-scripts` npm install unexpectedly gives plugins esbuild's mature delivery model for free, while making dist's npm installer useless, since its postinstall never runs and its first-run download lands inside a hook. Temper and Weigh-In should therefore differ on purpose. Weigh-In is a fail-soft ledger shipped as an uploaded zip, so bundling is right for it; the empirical check found its x86_64 musl build already covers both places Cowork runs code. Temper is a fail-loud enforcer shipped through a marketplace to Rust developers who already have Node and cargo, so the npm route fits it, provided the hooks only resolve the binary and never fetch or build it. The Cowork probe adds one condition: the auto-install does not run for claude.ai-synced plugins there, so if temper is to work in Cowork, its uploaded zip must also carry the binaries under `libexec/<target>/`, as Weigh-In's does.

The one uncertainty that could reverse this is cloud Cowork. If the probe shows no `node` or no npm auto-install there, the bundled-zip-plus-`sh` path that Weigh-In already runs becomes the Cowork channel for both plugins. Anthropic's own plugins already assume that combination is present, a POSIX shell and nothing else.
