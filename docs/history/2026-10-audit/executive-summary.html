temper · status review · 6 October 2026 · version 1.3.0

temper is built and in use. v1 needs about two weeks of pilot time and a handful of owner switches.

temper is a Claude Code plugin. It holds AI coding agents to the Wet Ink Rust quality standard and enforces that standard automatically. This review compares what has been built against the original vision, the road to v1 and the 2.0 rewrite plan, and sets out what is left.

The verdict

B

The product delivers the vision. Every capability the README promises exists and works. The automated checks pass, and two real projects run temper in their pipelines; one has already cleared all 721 of its inherited code-quality issues with it. What remains for v1 is mostly verification, housekeeping and calendar time, not new features. The grade is B rather than A for three reasons. Some protection settings the documents describe as switched on are switched off in GitHub. The pilot trial is only a few days old. And the most important "you may not stop until this is green and reviewed" logic has no automated tests.

Against the original vision

The vision is a Rust standard that agents follow whether or not they choose to, backed by automatic enforcement and an independent review before work counts as done. That is what exists today: ten layers of enforcement, five commands, three specialist agents and a 182-rule standard with tested examples. The evidence that it changes agent behaviour is real but narrow. On the tests built to tell the difference, agents with temper clearly do better. Averaged over every test, the lift is a more modest +0.31.

The vision is met less fully in two places. About half the rules (86 of 182) are checked only by the AI reviewer, not by tools. And the enforcement inside a session is best-effort, not tamper-proof: an agent working through shell commands could get around it. The CI pipeline stays the real backstop.

What is working well

  • The promise is real. Every feature in the README exists in code and behaved as documented when the audit tried it by hand.
  • The checks are green. 155 of 156 tests pass, all 2,757 rule cross-references resolve, and every example in the standard compiles or triggers the warning it claims to.
  • It works on real, messy code. weigh-in cleared all 721 inherited issues in three days. redkiln-rs, a codebase of about 236k lines, runs temper on its build branch.
  • Releases are disciplined. In five days, 31 pull requests merged and every one went through review. Versions, changelog and copies are cross-checked automatically.
  • It is light at runtime. Each action adds about a tenth of a second, and the scanner reads 13,000 lines in 64 ms.
  • Past review findings were closed. Of about 30 spot-checked items from earlier reviews, none was quietly dropped, and all 21 owner decisions can be traced.

What is holding things back

Merge protection is described but not switched on

owner · minutes

The docs say nothing can reach temper's main branch, which is what every user installs, unless CI passes. GitHub's rules on that branch require a pull request but no passing checks. The same holds for the pilots: weigh-in does not require temper's check, and redkiln-rs's adoption branch has no rules at all. The audit confirmed this directly against GitHub's settings.

The most important logic has no automated tests

1–3 days

The logic that stops an agent from finishing before its work is green and independently reviewed is tested only by occasional paid AI runs. A regression could ship unnoticed and then be copied into the 2.0 rewrite.

Review records can be faked from the shell

under a day

Direct file edits to temper's records are blocked, but shell commands are not. A misbehaving agent could write an "approved" review, or switch the end-of-turn check off by breaking a toolchain file. CI still catches code problems, but nothing outside the session re-checks the review.

The pilot isn't producing evidence yet

2 weeks elapsed · a few days of effort

The plan calls for two weeks of daily use plus data on blocks, false alarms, timings and review rounds. About three days have passed and nothing is being recorded. Gate time on the large redkiln-rs codebase has never been measured.

Running cost is undocumented

1–2 days

Loading the standard costs about 4,000 tokens, each reference adds 9–22k, and each review round adds 25–30k. None of this is written down, and CI spending alerts are not set.

Trackers and plans lag reality

under a day

The go-live checklist shows nothing ticked although about half is met. Some "done" claims in the plan are wrong. The rule "no urgent bugs open" cannot be checked because no priority labels or milestones exist. The 2.0 plan predates 1.3.0 in several places.

The first run on a brand-new project is rough

about a day

There is no step-by-step guide for a new project. An empty project shows a confusing error, and minimum Node and Claude Code versions are not checked.

Only the owner can do these

Most of these are settings changes that take minutes, but no agent can make them.

  • Require the Checks and Unit tests (Windows) CI checks on temper's main branch.
  • Require temper's gate check in weigh-in, and protect redkiln-rs's adoption branch.
  • Set GitHub Actions spending alerts at 75% and 90%.
  • Revoke the one-time crates.io token, then set up trusted publishing for crates.io and npm.
  • Decide whether v1 is the current 1.3.0 or a post-pilot release, and approve about $9–12 for a fresh eval run if it is a new release.
  • Ask another Wet Ink org member to test the install.
  • Create priority labels (or reword the "no P0/P1" rule) and add a second owner on the package registries.

The realistic path

  1. This week
    The owner switches on the required checks and spending alerts. In parallel: start capturing pilot usage data and measure gate time on redkiln-rs; add automated tests for the stop-and-review logic; close the shell loopholes; bring the plan and trackers up to date.
  2. ~17 Oct
    The two-week pilot trial can end. Then fix what it found and decide which release is v1. A new release needs a fresh eval and smoke run.
  3. ~20 Oct
    v1 live. A second org member confirms the install, the announcement goes out, and the go-live checklist is ticked and closed. Effort to here is about 3–5 working days spread over about two calendar weeks, plus 4–6 days of recommended hardening.
  4. Late Oct
    2.0 preparation, about 1–2 weeks: update the rewrite plan for 1.3.0, finish publishing setup and set up staged CI.
  5. Nov–Dec
    temper 2.0. The Rust rewrite, roughly 6–10 weeks of elapsed time. The limit is mainly how fast one owner can review and approve. Users stay on 1.x, untouched, until the switch-over.
