# Crate charter: `temper-app`

## Purpose
temper's use cases: one per subcommand and hook handler, and the ports they reach the outside world through (`Files`, `ProcessRunner`, `Clock`), plus the git and cargo command wrappers built on `ProcessRunner` (port plan §1.3). Phase 1d.2 brings the first use case, `temper scan --all` and `temper scan FILES` (`Engine::scan`), with 1.x's project discovery (the git top level first, through `ProcessRunner`), crate lookup and path rules. Phase 2b brings `Engine::hook` with the `post-tool` and `user-prompt` handlers, the skill markers, telemetry with rotation, and the state dir and config in discovery. Phase 2c brings the `pre-edit` handler, with Cargo's workspace-root rules for the manifest checks. Phase 2d brings the `pre-bash` handler's shell-independent checks. Phase 2e brings 1.x's shell reader (`hooks::shell`, crate-private, OC-1) with the state-dir and protected-configuration checks it serves.

## Layer
application.

## Allowed dependencies
- Workspace crates: `temper-domain`.
- Third-party, added by the phase that first uses it (D10): `serde_json`, `thiserror` (both in since Phase 1d.2). Dev only: `proptest` (in), `insta`, `tempfile`.

## Public surface
Re-exported from `lib.rs`, one path each (API-14):
- `Engine` (`new(ports, env, scanner)`, `scan`, `hook`), `RunEnv` (`cwd`, `style`, `plugin_data`, `temp_dir`, `remote_session`; since 2e `home`), `ScanArgs` (`targets`, `format`), `ScanTargets` (`All`, `Files`), `OutputFormat` (`Text`, `Json`), `CommandOutput` (`stdout`, `stderr`, `exit`), `Exit` (`Ok`, `Fail`, `Usage`), `CommandError` (`Refused`, `Files`, `Json`).
- The hooks (2b): `HookInput` (`parse`), `HookInputError`, `HookError` (`Files`, `NullInput`, `NotPorted`; since 2c `InputType` and `Glob`; since 2d `Setup`). `Engine::hook` answers `post-tool`, `user-prompt`, since 2c `pre-edit`, and since 2d `pre-bash`, with its 2e branches since 2e and without its 2f ones.
- The ports: `Ports` (`files`, `process`, `clock`), `Files` (`read_text`, `read_dir`, `real_path`; since 2b `stat`, `write_atomic`, `append_line`, `create_dir_all`, `rename`), `FileMeta` (`len`; since 2e `kind`), `DirEntry` (`name`, `kind`), `EntryKind` (`Dir`, `File`, `Symlink`, `Other`), `FsError` (`new`, `op`, `path`, `source`), `FsOp` (`Read`, `ReadDir`, `RealPath`, `Stat`, `Write`, `Append`, `CreateDir`, `Rename`), `Clock` (`now`).
- The process port: `ProcessRunner` (`run`), `ProcessRequest` (`program`, `args`, `cwd`, `stdout_cap`, `stderr_cap`, `timeout`; no `env` until Phase 4, OC-8 B), `ByteCap` (`new`, `get`), `ProcessOutput` (`status`, `stdout`, `stderr`), `ExitKind` (`Code`, `Signal`, `TimedOut`), `Stream` (`Stdout`, `Stderr`), `ProcessError` (`Spawn`, `Io`, `Overflow`).

Everything else is `pub(crate)`: the lexical port of Node's `path.posix` and `path.win32` in `paths` (OC-1 B), `paths::clean_rel` (2-26), `project` (`discover`, `discover_at` with `Workspace`, `crate_of`, `exists`, `declares_package`, `after_line_start`, `is_js_space`), `relpath` (`rel_to`), `git` (`toplevel`, `common_dir`; since 2e `short` with `Short`, 1.x's 5 s `run` that tells a failed git from one that did not run), `scan` (`walk`), `manifests` (`workspace_root_for` with `RootFor`, `own_lints_member`; 2c), `hooks` (dispatch through `HookCall` with `workspace_for_file`, `input`, `skill` with `skill_loaded`, `pre_edit`, `pre_bash` with `state_dir` and `protected` since 2e, `shell` since 2e (`parse_commands` with `Command`, `Word` and `TooLong`, `command_writes`, `command_deletes`, `patch_command` and `patch_files`, `resolve_path`, `js_len`), and `answered`, `logged` and since 2e `logged_then`, which write a decision's telemetry row before its answer) and `telemetry` (`log`). The in-memory fakes in `fakes` are `#[cfg(test)]` until another crate's tests need them; then a `test-util` feature exposes them (TST-09).

## Invariants
- No `std::fs`, `std::process` or `std::env`: files, processes, the clock and the run environment come through ports or `RunEnv` (ARC-02).
- The ports are traits owned here; adapters implement them, never the other way round.
- Path text follows Node's rules for the `RunEnv`'s `PathStyle`, not the host's, so both styles are tested on every platform.

## Errors
A typed error per use case family, wrapping port and domain errors with `#[from]` (ERR-01, H-09): `CommandError` for the commands, with `Refused` carrying 1.x's stderr text and exit; `FsError` (operation, path, `io::Error`) for the `Files` port; `ProcessError` (program plus cause, or the stream and cap that overflowed) for `ProcessRunner`, where a timeout or a failing exit is an `ExitKind`, not an error. Each 1.x fallback that swallows a failure is an explicit `match` arm with its reason (H-10): an unreadable target or manifest is skipped, an unresolvable path keeps its lexical form, `exists` is false, and any failed git run means no git root.

## Test strategy
- Unit tests against the fakes; no real processes or files.
- Node's path functions are checked against values printed by Node 22, and as properties in both styles (TST-06).
- Tests that need real git, cargo or the file system live in `temper-cli/tests/it` and run through the composition root.
- Run: `cargo test -p temper-app`.

## Do not
- Do not decide policy that belongs in `temper-domain`, and do not hold message texts; an error's own `Display` is not one.
- Do not call the standard library's process, file or environment APIs directly.
